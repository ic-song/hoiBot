# 계정·플랫폼 데이터 모델 표준

## 목적

이 문서는 포털계정, 게임계정, 대표·부계정, KakaoTalk·Discord 사용자, 방·서버별 활성 게임계정과 신규·레거시 인증 흐름의 단일 기준이다.

## 확정 관계

```text
포털계정 1 : N 게임계정
포털계정 1 : 1 대표 게임계정
포털계정 1 : N 부게임계정
플랫폼 사용자 1 : N 방·서버 참여
방·서버 참여 1 : 0..1 활성 게임계정
게임계정 1 : N 방·서버별 활성 선택
```

- 게임 데이터의 소유자는 게임계정(`player_id`)이다.
- 포털계정은 로그인, 약관, 결제·프리미엄과 게임계정 관계를 관리한다.
- 최초로 연결이 완료된 게임계정은 `REPRESENTATIVE`, 이후 계정은 `SUB`다.
- 대표·부계정의 포인트, 아이템, 펫, 가구와 기록은 서로 분리한다.
- 한 플랫폼 사용자가 한 방·서버에서 사용하는 활성 게임계정은 정상 상태에서 정확히 하나다. 미인증·정지 상태에서는 없을 수 있다.
- `/계정변경 [게임계정]`은 실행한 방·서버의 활성 `player_id`만 바꾸며 다른 공간의 선택과 게임 데이터는 바꾸지 않는다.

## 플랫폼 식별 범위

- KakaoTalk 오픈채팅 식별자는 방 범위다. 같은 사용자가 A방과 B방에 참여하면 각 방에서 최초 1회 인증한다.
- Discord 식별자는 플랫폼 계정 범위다. 같은 Discord 계정이 여러 서버에 참여할 수 있고 활성 게임계정은 서버별로 선택한다.
- 공통 식별 원칙은 `플랫폼 + 식별 유효 범위 + 외부 사용자키`다.
- 닉네임은 식별키가 아니다. 인증 당시 동일성 보조 검증과 표시 용도로만 사용한다.
- 같은 안정 사용자키에서 닉네임만 바뀌면 계정 연결은 유지한다. 사용자키가 바뀌면 재인증한다.

## 신규 회원가입

```text
포털 회원가입·최초 닉네임 입력
→ 인증 대기 포털계정
→ 1회용 코드 발급
→ 플랫폼에서 /인증 [8자리]
→ 현재 방 닉네임과 입력 닉네임 일치 확인
→ 신규 게임계정 생성
→ 대표계정 연결
→ 플랫폼 사용자·방 참여·활성 player_id 저장
→ 포털계정 활성화
```

게임계정, 관계, 인증 소비, 감사와 outbox는 한 트랜잭션에서 성공하거나 모두 롤백한다.

## 기존회원 동기화

```text
기존 레거시 게임계정 존재
→ 포털 회원가입·기존 닉네임 입력
→ 레거시 연결용 1회용 코드 발급
→ 기존 플랫폼에서 /인증 [8자리]
→ 현재 닉네임과 기존 게임계정 닉네임 일치 확인
→ 새 게임계정을 만들지 않고 기존 player_id 연결
→ 기존 게임 데이터를 그대로 보존
→ 최초 연결이면 대표계정, 후속 연결이면 부계정
```

레거시 동기화는 대상 게임계정이 다른 포털에 연결되지 않았고 플랫폼 사용자키도 다른 포털에 귀속되지 않았을 때만 허용한다.

## 명령 처리

```text
명령 수신
→ 플랫폼·외부 사용자키·방/서버 context 확인
→ 인증된 포털계정 확인
→ 해당 context의 활성 player_id 하나 확정
→ 명령 종료까지 같은 player_id 사용
→ 해당 게임계정 데이터로 실행
```

기존 `external_identities.player_id`만으로 사용자를 결정하는 소비자는 방·서버별 활성계정을 지원하지 못한다. 공통 actor-context resolver를 통해 점진적으로 전환하며, 전환 전 호환 경로와 전환 후 경로의 parity를 검증한다.

## DB 구현 원칙

- 적용된 migration은 수정하지 않고 신규 additive migration만 사용한다.
- 신규 PK는 대상이 드러나는 이름의 CUID2 8자리 `CHAR(8) ascii_bin`을 사용한다.
- 단독 `id`와 오브젝트·계정 식별용 `CODE`를 새 테이블에 만들지 않는다.
- FK 컬럼은 참조 PK와 이름·타입·길이·문자셋·collation을 일치시킨다.
- 모든 신규 정의·관계·이력·운영 테이블에 `INSERT_USER`, `INSERT_TIME`, `UPDATE_USER`, `UPDATE_TIME`을 둔다.
- 시간은 KST 24시간 문자열 `YYYY-MM-DD HH:MM:SS`를 사용한다.
- 대표계정 유일성, 게임계정의 중복 포털 귀속, 플랫폼 사용자키의 중복 포털 귀속과 방·서버별 활성계정 1건을 DB 제약과 트랜잭션 잠금으로 함께 차단한다.
- 인증번호 원문은 저장하지 않고 hash, 목적, 대상 포털·게임계정, 플랫폼·context, 만료·실패 횟수와 소비 상태만 저장한다.
- 닉네임 변경 이력은 표시·감사용이며 소유권, 권한, 재화·아이템 처리의 키로 사용하지 않는다.

## WBS 경계

- `SL-ACCOUNT-MULTI-GAME-PLATFORM-CONTEXT-01`에서 Gate 1~7을 수행한다.
- Gate 1~4의 schema·인증 provider·합성 검증은 오브젝트 소비자 전환과 겹치지 않는 별도 작업공간에서 진행할 수 있다.
- `app.ts`와 전체 게임 명령의 actor-context 전환은 `SL-OBJECT-DB-CONSUMER-PARITY-01`과 파일·소비자 범위가 겹치므로 해당 작업 뒤 Gate 5~7에서 직렬 통합한다.
- migration `466`과 오브젝트 계약은 변경하지 않고 계정·플랫폼 증분 migration은 `467~469` 범위로 예약한다.
- 운영 DB, 운영 데이터, `feature/prod`와 Gate 8은 사용자 승인 전 변경하지 않는다.
