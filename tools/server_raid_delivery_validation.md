## 변경과 판정

`scheduleServerRaidWork`의 공지 전송 실패에서 전체 순회를 멈추는 동작을 제거했다. 작업 한 번 동안 실패한 방을 기억하고 그 방의 후속 공지만 보류한다. 다른 방은 계속 전송하며, 다음 예약에서 저장된 미발송 방을 다시 시도한다. 방별 공지 순서, 완료 방 생략, 기존 환경별 단일 예약, 회차/세대 검사, 회원 저장·정산 경계는 유지한다.

| 요구·예외 | 확인 결과 |
| --- | --- |
| 수정 전 원인 재현 | 기존 운영 소스로 새 회귀를 실행하면 정상 방의 완료 검사 실패. 수정 후 통과 |
| 한 방의 false/예외, 전송·로그 동시 예외 | 실패 방만 남고 뒤의 정상 방·후속 공지 완료 |
| 첫/중간/마지막 방, 여러 실패 방 | 각각 독립 재시도, 성공한 방의 완료 공지는 재발송 없음 |
| 방별 순서 | 실패 방의 첫 공지 뒤 후속 공지는 보류, 연결 복구 뒤 기존 순서대로 발송 |
| 이전 회차 결과 1건만 미발송 | 새 회차 준비·시작은 다른 방으로 정상 발송 |
| PREP 재시작 | 저장 시각으로 재개, 늦은 활성화부터 30분, 오래된 준비 안내 취소 |
| ACTIVE 재시작·마감 후 재시작 | 원래 마감 유지/즉시 종료, 정산 1회, 정상 방에 종료·결과 발송 |
| SETTLING 일부 지급 후 재시작 | 미지급자만 지급, 상금·핸디캡·우승·완료 횟수 중복 없음 |
| 완료 회차·미발송만 재시작 | 대전 재생성 없이 미발송 방만 재시도 |
| 발송 완료 저장 실패 | 후속 전송 중단, 저장된 완료 방 보존, 새 VM에서 미확정 방 재개 |
| 완료 저장 직후 강제 중단 경계 | 저장된 디스크를 새 VM으로 복원해 완료 방 생략 |
| 읽기 예외·누락·손상 JSON | 빈 상태 초기화/덮어쓰기 없음, 기존 오류 흐름 유지 |
| DEV/PROD | 저장·공지·예약 격리, DEV는 다음 DEV 요청으로 재개 |
| 전체 초기화·오래된 예약 | 이전 콜백이 상태·공지·보상을 변경하지 않음 |
| 모든 방 실패 | 자동 종료·정산 완료, 환경별 예약 1개, 연결 복구 후 발송 완료 |
| 발신자 | MASTER와 인증된 운영봇의 회차·공지 처리 동일 |

## 검증 범위와 남는 경계

- Android MessengerBot 앱 강제 종료·실제 답장 세션 재획득은 직접 실행하지 않았다. 개발 PC의 새 Node VM 및 Rhino 전역 환경으로 저장 복원·예약·정산·공지 재개를 검증했다.
- 연결이 없는 방은 연결 복구 전까지 기존 2초 간격으로 재시도한다. 이번 수정은 그 실패가 다른 방을 막는 문제를 해결한다. 앱 답장 세션 자체를 생성하지 않는다.
- 메시지를 실제 발송한 직후 완료 상태 저장 전에 프로세스가 중단되면 해당 공지는 중복될 수 있다. 기존 전송/저장 사이 경계이며, 저장된 완료 방의 재발송과 보상 중복은 방지한다.
- 운영 반영 승인 후 버전·개발자노트의 반영일을 갱신하고 소스 브랜치 검증 → 원격 prod 반영·검증 → 기존 노션 대응 문서 속성 갱신 순서를 진행한다.
