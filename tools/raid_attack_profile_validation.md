# 레이드 공격 계측·최적화 개발 검증

- 기준: `96633c05dd0c6eb66e24f6fb786bcae7a4c3fc62` / `ver_2.664`
- 작업: `feature/bugFix`, 2026-10-21, 운영반영 전 검토
- 데이터: 합성 입력만 사용. 운영 앱·기기 접근과 운영 Git 반영은 하지 않았다.

## 계측 조건과 범위

PC의 Rhino 1.7.15 인터프리터에서 현재 소스의 공격 분기·게임 계산·저장 함수를 실행했다. Java UTF-8 파일 읽기/교체와 실제 `fsync`를 유지했다. 전후 같은 합성 회원 데이터와 과거 회차를 사용했다. 회원에는 약 1.4MB의 합성 본문, 회차 이력에는 270KB 본문 12개, 운영 로그에는 44KB 본문 4개를 추가했다. 실제 운영 데이터 크기나 내용의 재현을 의미하지 않는다.

구간 계측의 펫 기본 매력은100,000, 인형 요약 매력은20,000이며 장비/가구/스킬 슬롯은 비어 있고 프리미엄은 꺼진 조건이다. 실제 매력·치명타 함수는 실행하지만 모든 장착 조합의 계산 비용을 나타내지는 않는다. 별도 기존 회귀에서 옵션/스킬/매력 수식의 정확성을 검증했다. 참가자가 많은 경우의 순위 생성 비용은 아래 독립 시험에서 확인했다.

각 소스는 별도 Java 프로세스에서 준비 실행 5회 후 10회를 측정했다. `System.nanoTime`으로 구간을 쟀다. 아래 중위는 정렬된 10개 중 인덱스 5의 값이다. 구간별 중위의 합은 전체 중위와 다를 수 있다. 운영 기기의 Android 성능, 실제 경합 대기, 카카오 전송 시간은 측정하지 않았다. 자격을 갖춘 공격 분기의 처리 시간을 재며, 전체 콜백의 공통 전처리 시간은 포함하지 않는다. 실제 전체 7인수 콜백의 잠금/문맥/전송 경계는 별도 시험했다.

이 조건에서는 저장이 전체 시간의 약 86%였다. 전체 약 22.2%, 저장 약 28.9% 감소했다. 읽기는 26,666,427→25,263,749바이트, 16→15회다. 저장 내용·쓰기량·동기화 4회는 유지한다. 무경합 잠금 대기는 약 0.02ms 이하였으며 실제 운영 대기시간을 뜻하지 않는다. 전후 전체 회원·레이드 결과와 각 공격 메시지의 일치를 단언했다.

초기 측정과 최종 측정 사이에 수 ms 단위의 편차가 있었다. 고정된 Android 지연 감소율을 보장하는 수치로 해석하지 않는다. 런타임에 상시 계측 로그나 진단 파일 쓰기를 추가하지 않았다.

## 참가자가 많을 때 공격 응답 계산

공격 안내는 서버 누적 데미지와 서버 순위만 표시하지만 기존 `buildServerRaidResults`는 개인 순위도 전부 정렬했다. 공격 안내만 개인 정렬을 건너뛰도록 선택 인수를 전달한다. 서버별 정확한 큰 정수 합산과 공동 순위 계산은 유지한다. 조회·종료 정산의 기존 호출은 개인 정렬을 유지하며, 정산(`freeze === true`)에서는 생략 옵션을 줘도 개인 결과를 반드시 확정한다.

실제 Rhino에서 같은 참가자/공격 안내를 준비 5회·측정 10회로 대조했다. 저장과 네트워크 시간은 이 시험에 포함하지 않았다.

| 합성 참가자 | 기존 문구 생성 중위(ms) | 수정 중위(ms) | 관찰 |
| --- | ---: | ---: | --- |
| 100명 | 18.01 | 24.99 | 표본 편차로 개선 확인 안 됨 |
| 1,000명 | 49.58 | 21.30 | 약 57.0% 감소 |
| 5,000명 | 307.40 | 69.42 | 약 77.4% 감소 |

원본 표본: [raid_attack_ranking_result.json](raid_attack_ranking_result.json). 개인 정렬 비용이 커지는 대규모에서 개선이 뚜렷하다. 참가자 전체 순회와 서버 합산은 매 공격 여전히 수행한다. 공격 메시지와 최종 개인/서버 정산 객체가 전후 동일함을 검사했다. Node에서는 1,500명, 공동 1위, 공격 없는 계정, 빈 회차, 안전 정수보다 큰 누적 피해를 추가로 대조했다. 공격 안내의 순위 정렬 호출은 서버용 1회임을 확인했다.

## 저장과 전송 변경

1. 이미 직렬화한 분리 데이터 본문을 재사용해 같은 JSON을 구성한다.
2. 방금 읽고 검증한 분리 원문을 비열거 속성에 잠시 보관해 백업에 사용한다. 디스크 형식에는 새 속성을 추가하지 않는다.
3. 같은 저장 잠금 안에서 새로 읽고 검사한 회원 원문/파싱 결과를 백업에 전달한다. 명령 간 캐시가 아니며 최신 세대 검사와 누락/손상 오류는 유지한다.
4. `/레이드공격` 응답은 저장/롤백과 두 잠금 해제 후 원래 응답 객체로 전송한다. DEV 헤더·문맥은 유지한다. API와 오류 로그가 동시에 실패해도 이미 저장한 공격을 되돌리지 않는다.

실제 전체 `response(...)`를 Java 스레드와 latch로 실행했다. 기준 코드에서는 첫 응답 API를 정지하면 후속 공격과 턴 조회가 기다렸다. 수정본에서는 첫 응답의 반환 전에 후속 공격 저장과 턴 조회가 완료됐다. 두 공격의 피해/포인트/횟수와 각 응답의 남은 턴을 대조했다. 응답 순서는 네트워크 지연 시 달라질 수 있으며, 각 메시지는 해당 공격 시점에 확정한 결과다. 정지된 API 자체의 호출 스레드는 반환을 계속 기다린다.

## 재현

저장소 루트에서 실행한다. Rhino JAR은 Maven Central의 `org.mozilla:rhino:1.7.15`이며 제공된 SHA-256과 대조했다. 테스트 의존성으로만 사용하며 운영 봇 코드에 추가하지 않는다.

```powershell
node tools/test_raid_attack_profile.js
node tools/test_raid_attack_profile_rhino.js <rhino-1.7.15.jar> <profile-result.json>
node tools/test_raid_attack_ranking_rhino.js <rhino-1.7.15.jar> <ranking-result.json>
node tools/test_raid_attack_reply_rhino.js <rhino-1.7.15.jar>
```

성능 계측 스크립트는 다른 CPU/디스크 집중 시험과 동시에 실행하지 않는다. 현재 보고서는 개발 PC의 합성 검증이며 운영 단말의 실측 결과가 아니다. 운영반영은 별도 요청 이후 버전/개발자노트와 원격 운영 브랜치를 검증하는 절차로 진행한다.
