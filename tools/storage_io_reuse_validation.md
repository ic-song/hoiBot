# 저장 내부 중복 작업 감소 재검증

- 운영 기준: `91fc5ba09123a1dd4a7b30097ec502e540f00be1` / `ver_2.665`
- 준비 버전: `ver_2.666`, 2026-10-21 KST
- 작업 브랜치: 최신 local `feature/prod`에서 분리한 `feature/storage-io-reuse`
- 사용자 범위: 저장 내부 중복 읽기·파싱·직렬화만 개선. 백업과 복구 유지, 최신 운영 기준 재검증 후 운영 반영.

## 구현 경계

1. 변경 비교에 이미 사용한 로그/레이드 JSON 본문으로 분리 저장 JSON을 구성한다. 기존 canonical JSON과 동일함을 검사했다.
2. 분리 파일을 새로 읽고 검증한 원문을 비열거 속성에 잠시 연결해 해당 백업 호출에 사용한다. 새 속성을 파일에 저장하지 않는다. 백업 원문은 매번 필요한 시점에 새로 읽는다.
3. 같은 저장 잠금에서 방금 읽고 세대를 검사한 회원 원문과 파싱 객체를 백업에 전달한다. 분리 회원의 정확한 경로에서만 재사용한다. 다른 파일과 일반 저장 호출은 기존 읽기/검증을 수행한다.

명령을 넘는 파일 캐시, 백업/fsync 생략, 손상 자동 무시, 지연 일괄 저장은 추가하지 않았다. 기존 1·2차 백업 회전 시점, 세대 일치 검사, 임시 파일 재검증, 원자 교체, 저장 실패 롤백과 명시적 복구는 유지한다. 공격 수식/보상/응답/공지 동작도 최신 운영과 같다. 이전 PR #138의 응답 전송 잠금 변경은 이번 반영에 포함하지 않는다.

## 최신 운영과 대조한 예외

`tools/test_storage_io_reuse.js` 21그룹:

- 한글·이모지·따옴표·개행·배열·중첩 JSON의 저장 직렬화 동일
- 검증 원문의 비열거 속성이 저장되지 않음, 백업에서 원문 보존
- 저장 직전 회원 누락/손상과 로드 뒤 레이드/로그 손상 거부
- 레이드 슬롯·회원·레이드 백업·회원 백업 교체4지점 및 fsync4지점 실패
- 실패 뒤 전체 원본/백업 파일을 기준 소스의 같은 실패 결과와 대조, 같은 공격 재시도/재전송 지급1회
- 같은 객체 연속 저장 후 전체 롤백, 오래된 객체 저장 거부
- 새 VM 재시작 뒤 기존 공격/보상/횟수 복원·원본 이벤트 중복 방지·이후 정상 정산
- DEV 성공/저장 실패/재시도와 운영 파일 격리
- 게임 핵심 함수 원문 동일, 저장 함수와 버전 외 main 실행 코드 전체 동일

일반 저장 실패는 기존 규칙대로 정상 직전 백업을 갱신할 수 있다. 무조건 모든 백업을 이전 바이트로 되돌린다고 가정하지 않고, 기준 소스와 전체 파일을 비교했다. 분리 저장 기존55그룹에는 1·2차 백업 복원·세대 불일치·중단된 분리 게시·명시적 백업 재구성·백업 회전 실패 롤백이 포함된다.

주요 Node257그룹: 저장 신규21 + 분리55 + 레이드130 + 공지18 + I/O12 + 추가 정책11 + 무쌍5 + 개인 정렬5. 기존 개인 정렬 시험의 main 전체 고정 비교는 관련 순위 함수 비교와 현재 버전/개발자노트 일치 검사로 좁혀 저장 변경과 함께 실행되도록 했다.

공통 저장 회귀: 펫스킬15, 인장/미니펫 조회11, 창조 보상상자8, 관리자 미니펫11, 포인트 상점25그룹과 베란다 명령·대규모 확장2스크립트 통과.

Rhino: 분리 저장35단언, 전체 MAIN/Info 컴파일·공지/실제 Java 동시성·재시작9시나리오, 기록실 실제 Java 파일·실패 복구·DEV·재시작5시나리오 통과. 아래 계측도 실제 Java 파일/동기화를 사용한다. 운영 앱이나 LDPlayer에는 접근하지 않았다.

## 같은 입력의 파일 I/O

1MB 합성 회원 본문과 1MB 과거 회차 본문을 넣은 독립 Node 시험에서 전후 최종 파일을 전체 대조했다.

| 항목 | 기준 | 수정 |
| --- | ---: | ---: |
| 읽은 바이트 | 11,039,986 | 10,038,424 |
| 읽기 호출 | 17 | 16 |
| 쓴 바이트 | 4,012,283 | 4,012,283 |
| 쓰기/fsync | 4 / 4 | 4 / 4 |

쓰기와 복구 보장을 유지한 채 회원 원문의 중복 읽기가 감소했다. 백업 첫 생성·2차 회전·추가 파일 변경이 있는 명령에서는 쓰기 수가 달라질 수 있다.

## Rhino 구간 계측

같은 합성 입력, Rhino1.7.15 인터프리터, 준비5회+측정10회. 단조 시계 `System.nanoTime`, 실제 Java UTF-8 파일과 fsync를 사용했다. 중위는 정렬된10개 표본의 인덱스5다. 각 소스는 별도 프로세스에서 실행하므로 PC 부하/파일시스템 편차가 있으며 구간별 중위의 합은 전체 중위와 다를 수 있다.

| 구간 | 최신 운영(ms) | 저장 개선(ms) |
| --- | ---: | ---: |
| 전체 공격 분기 | 415.58 | 345.20 |
| 회원·레이드 읽기 | 32.24 | 31.17 |
| 매력·치명타 계산 | 0.28 | 0.21 |
| 저장 | 378.90 | 309.62 |

전체 약16.9%, 저장 약18.3% 감소했다. 읽기26,666,427→25,263,749바이트, 16→15회이며 fsync4회다. 전후 전체 회원·레이드 객체와 각 공격 메시지가 동일했다. 표본은 `tools/storage_io_reuse_profile_result.json`에 있다.

회원 패딩1.4MB, 과거 회차270KB×12, 로그44KB×4를 사용했다. 펫 기본 매력100,000/인형 요약20,000이고 장비·가구·스킬 슬롯은 비어 있으며 프리미엄은 꺼져 있다. 자격을 갖춘 실제 공격 분기와 계산/저장을 실행하며 전체 콜백 공통 전처리·카카오 네트워크·Android 실기기 시간은 포함하지 않는다. 성능 계측 중에는 다른 집중 시험을 병렬 실행하지 않았다. 런타임에 계측 로그 쓰기를 추가하지 않았다.
