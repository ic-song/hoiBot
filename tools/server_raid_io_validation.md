## 원인과 변경

기존 예약 작업은 공유 데이터 잠금 안에서 공지 API를 호출했다. 공격은 이 잠금을 기다리는 동안 외부 명령 쓰기 잠금도 점유하므로 후속 조회도 대기할 수 있었다. 실제 Rhino/Java에서 데이터 읽기·저장이 즉시 반환하는 조건에서도 전송 지연만으로 이 잠금 사슬을 재현했다. 이 통제 실험은 운영 기기에서 어떤 API가 최초로 지연됐는지까지 확정하지 않는다.

준비·마감·정산과 공지 전송을 분리했다. 공지는 환경별 한 전용 Java 스레드에서 보내며 API를 호출할 때 데이터 잠금을 보유하지 않는다. 정산 지급도 공지 전송 완료를 기다리지 않는다. 방별 종료→결과 순서, 실패한 방만 재시도, 이미 확정된 성공 방 생략을 유지한다.

작은 보호 파일 `serverRaidNoticeReceipts.json`에 성공 영수증을 바로 저장한다. 전체 회원·레이드의 완료 표시는 한 묶음으로 반영한다. 최초 파일과 설치 표시는 한 트랜잭션으로 기록하고, 이후 파일 누락·손상·알 수 없는 버전·세대 불일치는 기본값으로 대체하지 않는다. 검증 임시 파일·fsync·원자 교체·트랜잭션 롤백을 사용한다. DEV 경로도 분리한다.

같은 묶음에서 반복 대용량 읽기를 피하되 회원 게시 번호가 바뀌면 다시 로드하고 성공 영수증을 합친다. 전송 중 공격·정산·초기화가 저장한 최신 회원 상태를 덮지 않는다. 회원 게시 번호는 검증된 회원 파일 교체와 롤백 때 증가하는 메모리 값이다.

로그와 레이드 백업 캐시를 각 버전으로 나눠 변하지 않은 운영 로그 백업을 공격마다 다시 쓰지 않는다. 정기 2차 백업은 원본 버전을 계속 검사하며, 명시적 백업 재구성은 캐시를 우회해 전체 복사한다.

## 논리 I/O 비교

합성 회원 본문 1.4MB 패딩, 과거 레이드 12회×270KB 패딩, 운영 로그 4종×44KB 패딩을 동일하게 준비했다. 실제 저장 함수/백업/검증 읽기를 메모리 파일시스템에서 계측했다. 실기기 wall-clock 성능 수치가 아니다. 구 기준도 같은 최신 합성 하니스에서 기준 커밋의 main.js를 주입해 실행한다. 운영 데이터를 변경용 입력으로 사용하지 않는다.

## 한계와 보존

- Android MessengerBot API 자체의 세션 오류는 별도다. 채팅 세션이 없는 방에는 발송이 계속 실패할 수 있다.
- 한 API 호출이 반환하지 않으면 해당 환경의 공지 작업은 그 호출을 기다린다. 공격·조회·자동 정산은 해당 전송의 데이터 잠금을 기다리지 않는다.
- 이미 API에 넘긴 한 메시지는 초기화 후 취소할 수 없다. 반환 뒤 후속 과거 전송을 중단한다.
- API 성공 직후 영수증 저장 전 강제 종료하면 실제 전달 여부를 알 수 없어 공지가 재전송될 수 있다. 영수증이 저장된 방은 재시작해도 다시 보내지 않는다. 보상 중복 지급과는 별개다.
- 데이터 저장 자체가 지연되거나 실패하는 경우는 기존 검증·잠금·오류 흐름을 유지한다. 모든 종류의 기기 무응답을 제거했다는 의미가 아니다.
- 운영 앱 업로드·컴파일·재시작·실제 카카오톡 발송은 수행하지 않았다. 사용자가 요청한 개발 검증까지 완료한 상태다.
- 1,157개 이전 데이터 해시와 비교했을 때 과거 다른 승인 작업의 개발자노트 변경 1개만 차이가 있었고 게임 스냅샷은 동일했다. 이번 작업의 Git diff에는 data/ 및 Info.js 변경이 없다.
